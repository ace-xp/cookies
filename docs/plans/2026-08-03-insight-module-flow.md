# 素材洞察模块 · 完整流程说明

> 面向接手人与评审。讲清楚这个模块**做什么、数据怎么走、每一步的结论是谁算出来的**。
> 不涉及代码细节，涉及实现的地方只说明「靠什么算」，因为这决定了结论能信到什么程度。
>
> 状态截至 2026-08-03，对应主干 `main`。

---

## 1. 这个模块解决什么

投放素材做出来之后，会发生两件事：钱花出去了，数据回来了。但**回来的数据和当初做素材的决策，是两套互不相通的东西**——报表里是「广告 AD-1001，花了 2.4 万，点击率 3.2%」，而做素材的人记得的是「那条是数字人口播、痛点开场、15 秒」。没人把这两边对上，所以每一轮都在凭印象重来。

素材洞察要做的就是把这两边接起来，并且让接起来的结论能留下来、下一轮能用上：

- **投后**：这批素材表现如何、是不是在衰退、差异到底是哪个变量带来的。
- **沉淀**：把上面这些结论固化成「经验」，人工确认过才算数。
- **投前**：下一轮做素材之前，能查到「以前在类似条件下什么有效」。

一句话：**让每一轮投放的结论，成为下一轮的输入。**

## 2. 主流程

```mermaid
flowchart LR
  A["数据接入<br/>平台数据进来"] --> B["分析素材库<br/>建立素材索引"]
  B --> C["内容分析<br/>把创意拆成变量"]
  A --> D["投后分析<br/>六个解释视图"]
  C --> D
  D --> E["报告中心<br/>汇总成复盘"]
  D -.方向不明确.-> F["实验中心<br/>专门验一个变量"]
  F --> E
  E --> G["经验库<br/>人工确认才算数"]
  G --> H["投前洞察<br/>下一轮引用"]
```

流程有两个关键设计，是这个模块和普通 BI 报表的根本区别：

**第一，结论必须能追溯到证据。** 任何一条经验都带着它的数据依据（多少素材、多长窗口、什么指标）和内容依据（哪些素材特征）。查经验的时候能一路点回原始数据。

**第二，系统不替人下结论。** 分析产出的是「候选经验」，必须有人确认、驳回或补齐依据之后才进经验库。样本不够时系统会明说算不出来，而不是给个看起来像那么回事的数字。

## 3. 十一个入口对应到流程哪一环

| 分组 | 入口 | 在流程里的角色 |
|---|---|---|
| 数据 | **数据接入** | 平台数据进来的口子。管数据源、导入任务、字段映射、素材映射、同步记录。**素材映射是全模块的地基**——把平台侧的广告对象对上我们自己的素材版本，这一步不对，后面全是错的 |
| 素材与分析 | **分析素材库** | 可分析素材的索引：版本、特征、血缘。回答「这条素材是从哪一版改出来的」 |
| 素材与分析 | **内容分析** | 把创意内容拆成**可比较的变量**（开场方式、时长、口播风格……）。没有这一步，投后分析只能告诉你哪条好，说不出为什么 |
| 工作 | **投后分析** | 模块的主战场，六个视图：指标总览、素材对比、趋势、疲劳、异常、驱动因素。详见第 4 节 |
| 素材与分析 | **实验中心** | 投后分析给不出明确方向时（变量混在一起、样本不够）的出口。专门设计一个只改一个变量的对照实验 |
| 经验与输出 | **报告中心** | 把投后分析和实验的结论汇总成一份复盘，确认后沉淀为候选经验 |
| 经验与输出 | **经验库** | 经验的最终归宿。确认 / 驳回 / 待复审 / 已失效，以及**修订**（新增版本，不就地改，历史可审计） |
| 工作 | **投前洞察** | 下一轮的入口。按当前项目组合历史素材、经验与证据，供策略和创意引用 |
| 治理 | **数据质量** | 监控新鲜度、缺失、口径、异常，以及修复队列 |
| 治理 | **能力运营** | 治理特征体系、指标字典、分析 Skills、评测集 |
| 治理 | **系统设置** | 样本门槛、观察窗口、确认权限、报告模板。**这里改了阈值，投后分析的判定会跟着变** |

## 4. 投后分析的六个视图

这六个视图**共用一次数据请求**，是有意的：如果拆成六次读取，「趋势里看到的」和「疲劳里算的」可能来自两个不同时刻的快照，页面自己会打架。

| 视图 | 回答什么问题 | 怎么算出来的 |
|---|---|---|
| 指标总览 | 这个窗口整体花了多少、效果如何 | 汇总，带口径说明和置信标注 |
| 素材对比 | 两条素材谁更好，差异算不算数 | 两两配对 + **归因阶梯**：只有当两条素材只差一个变量、且样本达标时，才判「可归因」；否则只给方向性观察 |
| 趋势 | 逐日走势 | 按天序列。**不足 4 天判「看不出来」**，不给走势结论 |
| 疲劳 | 素材是不是在衰退 | 把窗口切成前后两半对比，三条阈值判定。详见 4.1 |
| 异常 | 哪天的数据不正常 | **MAD（中位数绝对偏差）**，偏离超过 3.5 倍算异常。用 MAD 不用标准差，是因为标准差会被异常点自己抬高——越异常反而越不容易被发现。不足 5 天不判 |
| 驱动因素 | 表现差异是哪个内容特征带来的 | 按素材特征分组对照（有这个特征的 vs 没有的） |

### 4.1 疲劳的判定规则

现在的做法是：把观察窗口切成前半段和后半段，比较两段的点击率、转化成本、曝光量。

| 信号 | 门槛 |
|---|---|
| 点击率下滑 | 跌 20% 以上 |
| 成本恶化 | 涨 20% 以上 |
| 曝光放大 | 涨 10% 以上 |

判定：

- 曝光在放大 + 点击率在跌 → **疑似疲劳**（最典型的形态：钱越花越多、效果越来越差）
- 点击率在跌 + 成本在涨 → **疑似疲劳**（双向恶化）
- 只有一项恶化 → **需观察**
- 都没有 → **没有迹象**
- 不足 4 天 → 不给任何结论，置信压到「样本不足」

另外，疲劳视图**只列「排除不掉的解释」，不写「已排除」**。受众变化永远排除不掉——因为受众构成数据一条都没有接入。这是老实的做法，但也意味着它没有真正做到 PRD 要求的「区分数据延迟 / 受众变化 / 预算变化 / 真实衰退」。

> ⚠️ **这一节的规则全部是实现时定的，文档里没有出处。**
> `docs/03-asset-management-prd.md:188` 整节只有一句话：「识别随时间出现的曝光增大但点击/转化下降、频次上升、成本恶化等趋势，区分数据延迟、受众变化、预算变化和真正素材衰退。」它规定了**要看什么现象**和**要排除什么干扰**，但没有规定**怎么看**。前后半段对比法、三个百分比门槛、4 天下限，都是代码自己选的。

## 5. 每一环的结论是谁算出来的

这一节是评审时最该看的：**同样是「系统给的结论」，来源的可靠程度差别很大。**

| 环节 | 结论来源 | 说明 |
|---|---|---|
| 内容分析 · 特征提取 | 🤖 **模型** | 已接入统一模型网关。按素材类型有六套提取规格（小红书笔记、公众号文章、品牌广告、数字人、广告前贴、爆款复刻）。每次提取都记录用了哪个模型、哪个版本、消耗多少 token。**没配置可用模型时直接报错，不用模板糊弄** |
| 投后分析 · 六视图 | 📐 **规则计算** | 全部是确定性算法，没有模型参与 |
| 实验中心 · 组间对比 | 📐 **规则计算** | 与素材对比共用同一套对比引擎，两边不可能给出互相矛盾的判定 |
| 报告中心 · 发现归并 | 📐 **规则计算** | 同方向的对比归并成一条并标注「几组支持」；**方向打架时拒绝推任何一个方向**，改为指向实验中心 |
| 经验库 · 确认与修订 | 👤 **人工** | 系统只提交候选，确认权限可配置 |
| 数据质量 | 📐 **规则计算** | 新鲜度、缺失、口径校验 |

对外提供 44 个接口。

## 6. 当前边界

### 6.1 数据

**目前全部是人工录入的演示数据，尚未对接外部投放平台。** 这是既定安排——先把模块内部的链路做通，接入调试排在后面。

需要知道的具体情况：当前库里只有 3 个素材 × 7 天指标，且每个素材的点击率从头到尾几乎是直线（第一个素材整整 7 天在 3.16%–3.28% 之间波动）。所以疲劳视图三条全是「没有迹象」——**这是正确结果，不是算错**，数据里确实没有衰退。但也意味着疲劳、异常、驱动因素这几个视图目前没有被真正验证过。

仓库里有一份 `scripts/seed-insight-performance-demo.sh`，会生成 21 天、四条刻意设计的曲线（含一条标准疲劳形态：点击率 3.3% → 1.8%、曝光 8000 → 18000）。这份数据**没有导入**过当前项目，素材名对不上。

### 6.2 已知问题

**问题 1（会误报，建议尽快修）：曝光变化被天数差异污染。**

窗口切前后两半时，奇数天会切成「前 3 天 / 后 4 天」——后半段天生多一天，曝光就凭空多出三分之一左右，刚好压过「曝光涨 10% 算放大」这条线。当前页面上那个 **+40.6% 的曝光变化就是这么来的，不是投放在放量**。

后果不只是数字难看：疲劳判定的第一条规则就是「曝光在放大 + 点击率在跌 = 最典型的疲劳」。一旦接入真实数据、某条素材点击率下滑 20%，系统会直接盖章「疑似疲劳」，哪怕投放量一动没动。PRD 要求区分的四种干扰里，它连「预算变化」都没排除干净，反而自己造了一个假信号。

修法：前后半段比**日均**，不比总量，天数差异自动抵消。只动疲劳一处。

**问题 2（结构性，需单独排期）：投后分析完全没接模型。**

PRD `§10.2` 描述的形态是——用户提问「最近两周快手数字人为什么成本上升」，由 Codex 先调用数据完整性、Cohort、疲劳分析几个 Skill，再组织回答（可确认的事实 / 观察到的相关变化 / 不能排除的混杂 / 建议验证或行动 / 可点击的证据）。`§12` 也留了发起分析任务的接口位置。

现状是：这个对话入口不存在，六个视图全部由硬编码规则产出。而 PRD 要求的「区分数据延迟 / 受众变化 / 预算变化 / 真实衰退」，靠阈值判断在原理上就做不到。

需要澄清的是：**接模型不能替代问题 1 的修复。** 分工是「算数字归计算、解读数字归模型」，前后半段比总量错在算的环节，模型拿到的输入就是那个失真的 +40.6%，只会把错误讲得更有说服力。两件事互相独立。

工作量差别很大：问题 1 是半小时的局部修正；问题 2 涉及 Agent 网关、Skill 注册、分析任务落库，是一个新模块的量级。

### 6.3 与文档的偏差登记

模块建设过程中发现了若干处 PRD 之间互相冲突的地方（例如投后分析第三个视图，`03` 号文档写「驱动因素」、`19` 号文档写「Cohort 分群」），已逐条判定并把理由写在代码注释里。判定原则是**数据可得性优先**——Cohort 需要受众构成数据，而一条都没接入，那一格只能永远是空的。

## 7. 建议的下一步

按投入产出排序：

1. **修问题 1**（半小时）。它现在是个会主动误报的坑，且与将来接不接模型无关。
2. **导入真实形态的演示数据**（`seed-insight-performance-demo.sh`，改一下素材名对齐当前项目）。疲劳、异常、驱动因素三个视图目前等于没验证过。
3. **接入真实投放数据**。这是模块从「能跑」到「能用」的分界线。
4. **问题 2 的模型接入**，单独立项。
